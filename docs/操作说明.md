# cfnew-backup 内核更新

本仓库只更新已经存在的 Cloudflare Pages Direct Upload 项目 `cfnew-backup`（`https://cfnew-backup.pages.dev`）。来源固定为 `byJoey/cfnew` 最新正式 Release 的 `Pages.zip` 和 `SHA256SUMS.txt`。定时任务默认关闭。

## 不做什么

不创建项目，不改项目名、生产分支、环境变量、KV 绑定、兼容日期、DNS、SSL 或 VPS。不读取、不记录 UUID，健康检查只请求站点根路径。不修改独立面板仓库，也不在这里做 Loon 修复。上传目录里只有 `_worker.js`，没有 `wrangler.toml`、`wrangler.json` 或 `wrangler.jsonc`。

## 为什么不用 cfnewup

`byJoey/cfnewup` 的 workflow 每 6 小时用 tag 下载地址取最新 Release，`unzip` 后 `git push`。它不校验 SHA-256，不限制压缩包内容，也不对已经存在的 Direct Upload 项目执行 `wrangler pages deploy`。把 zip 或 Git 仓库推上去不能更新 `cfnew-backup`。

## 令牌

在 Cloudflare 创建专用于此仓库的 Account API Token：

- 权限只选 **Account → Cloudflare Pages → Edit**。API 角色名是 **Pages Write**。
- 资源只包含这一个账号。
- 不要添加 Workers KV、Workers Scripts、DNS、SSL 或 Account Settings。

Direct Upload 持续集成文档要求的权限是 Account、Cloudflare Pages、Edit。Workers 授权文档写明 API token 的 Pages Write 可以 “Create, update, and delete Pages projects and Pages content.” 这个权限是账号级的，不能缩小到单个项目。令牌可以部署或删除该账号里的其他 Pages 项目。请尽量把这个项目放在单独账号；如果账号里还有别的 Pages 项目，这是令牌本身的风险，不是 workflow 输入能限制的。

把下面两项加到仓库 **Settings → Secrets and variables → Actions → Secrets**，不要写进仓库或日志：

- `CLOUDFLARE_API_TOKEN`
- `CLOUDFLARE_ACCOUNT_ID`

本仓库不包含这些值，workflow 也不会在 pull request 里使用它们。

## 开启顺序

1. 合并后不要创建 `AUTO_UPDATE_ENABLED`，或保持它不是精确的 `true`。变量缺失、`false`、`True`、`1` 都会挡住定时部署。定时表达式是 `17 */6 * * *`（UTC 每 6 小时的第 17 分）。门关闭时只跑不含密钥的测试，并留下 “scheduled deploy did not run”。
2. Actions 里手动运行 **cfnew core update**，`mode` 选 **dry-run**。它校验 Release、安全解出 `_worker.js`，并请求 `https://cfnew-backup.pages.dev/`。正文必须正好是 `hello`。有令牌时，它只读取生产部署的 commit message，判断是不是本更新器写过的检查点。它不上传。首页没有版本号。
3. 再手动选 **deploy**。即使 Release 与线上相同也会部署，供第一次核对。命令固定为 `wrangler@4.164.0 pages deploy <隔离目录> --project-name=cfnew-backup --branch=main --commit-dirty=true --no-bundle`。没有项目名、账号或 Release 地址输入。
4. 部署后在仪表盘核对，并把结果留在仓库和 Actions 日志之外：
   - 项目名仍是 `cfnew-backup`，生产分支仍是 `main`
   - 兼容日期仍是 `2026-01-20`
   - KV 绑定名仍是 `C`，命名空间仍是 `cfnew-backup-config`
   - 生产文本变量仍在。不要复制变量值，不要访问变量值组成的路径
   - 访问地址仍是 `cfnew-backup.pages.dev`
   - 根路径仍返回 `hello`
   - Deployments 里仍能看到上一份成功记录
5. 以上都成立后，把 Actions Variable `AUTO_UPDATE_ENABLED` 设为 `true`。之后每 6 小时若最新成功生产部署的 commit message 与本次检查点完全一致，则跳过；读失败、部署未成功或 message 不同，就再部署同一版本。跳过不会修改项目设置。手动 deploy 始终可以重复部署同一 Release。

## 设置为何保留

Pages 文档 [Configuration](https://developers.cloudflare.com/pages/functions/wrangler-configuration/)（页面标注更新于 2026-06-25）写明：

> Once you are ready to deploy your project, you can set the configuration for production and preview deployments by creating a new deployment containing a Wrangler file.

同一页 Source of truth：

> If you decide that you do not want to use a Wrangler configuration file for configuration, you can safely delete it and create a new deployment. Configuration values from your last deployment will still apply and you will be able to edit them from the dashboard.

没有 `pages_build_output_dir` 的 Wrangler 文件只用于本地开发。Direct Upload 文档写明 Wrangler 上传的是单个文件夹，zip 不受支持；`_worker.js` 可以被 Wrangler 和拖放部署。

Wrangler `4.164.0` 的 `packages/wrangler/src/api/pages/create-worker-bundle-contents.ts` 在没有 Pages 配置时删除 `metadata.bindings`，避免上传空绑定数组。`compatibility_date` 和 `compatibility_flags` 只取自配置文件（`config?.compatibility_date`），没有配置文件时不会写入新日期。`wrangler_config_hash` 只在配置同时具备 `pages_build_output_dir` 时附加。`pages/deploy.ts` 在非交互模式下找不到项目会失败，并提示另行执行 `wrangler pages project create`；本仓库不会执行创建、删除、secret 或 KV 写入。`--branch` 会使这次部署不转入新建 Workers 项目的委托路径。

因此上传目录必须保持没有 Wrangler 配置，工作目录也不能向上找到这类文件。这是沿用现有仪表盘配置的条件，不是 Wrangler 对任意目录的无条件保证。第一次手动部署后，仍要用上面的仪表盘清单确认生产变量、KV 绑定 `C` 和兼容日期 `2026-01-20` 都还在。

上游 `v2026.10.17.2` 说明：上传新内核不主动清空 KV；应保留原来的 UUID、KV 绑定和域名。首页显示 `hello` 是正常现象。

## 压缩包

只接受正式、非 draft、非 prerelease 的 Release。先取 `/releases/latest`，再按该数字 ID 读取同一条 Release，并用资产数字 ID 下载，不使用可变的 tag 下载地址。`SHA256SUMS.txt` 必须正好两行、GNU `sha256sum` 的两个空格，文件名只有 `Pages.zip` 和 `_worker.js`。压缩包只能含根目录的 `_worker.js`。路径穿越、符号链接、目录、额外文件、加密、Zip64、声明体积或压缩比超限、CRC 不符都会失败。解压上限是压缩 512 KiB、解压 1 MiB、压缩比 40。当前正式包远小于该上限；超过上限会失败而不是放行。实现时用当时的正式包 `v2026.10.17.2`（Release `416271394`，`Pages.zip` 的 SHA-256 为 `d10345f660480c5b9d44b80e24fe77e094c98f7267285c616d76fed3946313c6`）走通了解析，只得到 37806 字节的 `_worker.js`，与 `SHA256SUMS.txt` 一致。workflow 仍跟随最新正式 Release，不把这个版本写死。

## 回滚

健康检查失败不会自动回滚。到 Cloudflare 仪表盘打开 `cfnew-backup` 的 Deployments，对上一份成功记录执行 Rollback。不要删除项目，不要修改 KV 命名空间 `cfnew-backup-config` 里的数据，不要改生产变量，不要上传带 Wrangler 配置的目录。回滚恢复的是那次部署的代码；它不会把后来写入 KV 的配置改回去。

## 限制

- 本任务没有令牌，不能代替你做第一次线上部署。
- Pages Edit 不能按项目缩小。
- Wrangler 仍会 GET 项目元数据，以便在没有配置文件时沿用已有兼容日期做本地兼容检查。响应里可能有变量值。workflow 强制 `WRANGLER_LOG=warn`、`WRANGLER_LOG_SANITIZE=true`，并去掉 debug、自定义 API 根地址和输出文件。不要打开 `ACTIONS_STEP_DEBUG`。
- job 不会用 `node` 执行 `_worker.js`。`--no-bundle` 上传原始文件；Wrangler 只用 esbuild 检查导入，不把产物写回。
- 资产被替换后，ID 或 SHA-256 对不上就失败。
- 检查点是部署 commit message，不是仓库写入，也不是项目设置。仪表盘手工上传没有这条 message 时，定时任务会再部署一次。检查点读不到时同样再部署，避免错误跳过。
- 并发组 `cfnew-backup-core-update` 排队而不取消正在进行的部署。
- pull request 只跑测试，不接收部署密钥，也不使用 `pull_request_target`。
